This file answers one question: does anything in this repository hand a secret
to whoever reads it? The short answer is no, and below is how that was checked
rather than assumed.

----------------------------------------------------------------------------
1. SEARCH FOR CREDENTIALS IN THE GAME CODE
----------------------------------------------------------------------------
Search run over every C# file under Assets/ for:

  (api[_-]?key | client[_-]?secret | password | bearer | private[_-]?key
   | BEGIN RSA | connectionstring)          ... case-insensitive

Result: NO MATCHES.

----------------------------------------------------------------------------
2. SEARCH FOR CREDENTIAL AND BUILD ARTEFACT FILES
----------------------------------------------------------------------------
The list of files Git actually tracks was scanned for:

  .keystore   .jks   .env   .apk   .aab   secret   credential   apikey   token

Result: NO MATCHES in the 190 tracked files.

There is no signing keystore in the repository either. On Android the upload
keystore is the one file that must never be committed - whoever holds it can
publish an update to the app under the same identity. It lives outside the
project, and .gitignore now blocks it even if it is ever copied in by mistake.

----------------------------------------------------------------------------
3. THE ONE PIECE OF KEY MATERIAL IN THE PROJECT, AND WHY IT IS NOT A SECRET
----------------------------------------------------------------------------
The profile is signed with HMAC-SHA256. Its key is not stored in the source:

  Assets/Scripts/Profile/PlayerProfile.cs, GetSaltBytes() (lines 361-374)

    - reads PlayerPrefs["profile.salt"]
    - if that value is absent or damaged, it generates 16 fresh random bytes
      (RandomNumberGenerator.Create().GetBytes) and writes them back to
      PlayerPrefs
    - the bytes never appear in the project, in Git, or in a log line

So there is no constant key that could be lifted out of the repository. Each
install derives its own key the first time it saves.

This is also the honest limit of the whole design, and it is recorded as L15
in pt5_checks.log rather than hidden: the salt lives on the same device as the
signed file, in PlayerPrefs. A determined local attacker with the device can
read the salt and re-sign an edited save. The signature makes tampering
EVIDENT - a hand-edited file is rejected and set aside - it does not make
tampering impossible. Only a server that the player cannot read would do that,
and an offline two-player board game has no server.

----------------------------------------------------------------------------
4. .gitignore
----------------------------------------------------------------------------
Added for this submission:

  # Mobile build outputs - never committed
  *.apk
  *.aab
  *.unitypackage
  *.keystore
  *.jks
  crashlytics-build.properties

  # Aura assistant working state (not part of the game)
  .Aura/
  Assets/.Aura/

Reasoning for each group:
  *.apk / *.aab        - build outputs. They are tens of megabytes, they are
                         rebuilt from source, and Git cannot diff them.
  *.unitypackage       - an exported package is a copy of what is already in
                         Assets/, so it only adds weight.
  *.keystore / *.jks   - signing identities. Committed once, they cannot be
                         un-leaked. This rule is the safety net described in
                         section 2.
  crashlytics-build.properties - a generated file that commonly carries
                         project identifiers and build secrets.
  .Aura/ , Assets/.Aura/ - the assistant's own plan and skill files. They are
                         tool state, not game content, and do not belong in a
                         submission about the game.

The rules were verified by re-checking that nothing matching them was already
tracked - a .gitignore entry does nothing for a file that is already in the
index.

----------------------------------------------------------------------------
5. WHAT IS STILL THE STUDENT'S RESPONSIBILITY
----------------------------------------------------------------------------
A clean scan is not a guarantee, and this file does not pretend otherwise:

  - It covers this repository only. Anything pasted into a chat, a document,
    a screenshot or a form is outside it.
  - The profile file itself is written to Application.persistentDataPath at
    runtime. It contains a display name and match results - no password, no
    email, no device identifier - so it is not a credential, but it is
    personal data and it stays on the device.
  - If a future week adds an online service, its keys must be handled the
    opposite way to the salt above: kept out of the client entirely and never
    read from PlayerPrefs.
