1. What was built

Dama now remembers the player. A profile panel reachable from the start screen holds a display name, the side the player takes (RED or BLUE), a win/loss/draw record with a win streak, and a local best-times board of the five fastest victories, each labelled with the match it came from. The record is stored in a signed JSON file in the app's own sandbox and survives closing and reopening the game.

2. Where the player meets it

  1. The start screen gains a PROFILE button under START.
  2. Pressing it puts DamaBoard into GameState.Profile, which hides every other panel and shows ProfilePanel.
  3. The player types a name (the store caps it at 16 characters and strips control characters), taps SIDE: RED to switch to BLUE if that is the side they play, and presses SAVE. The status line confirms.
  4. Playing a match to an end banks exactly one entry: win, loss or draw from the profile owner's side, with the winning side, the match clock in seconds and the pieces each side had left.
  5. Reopening PROFILE shows the updated record and, for a victory, a line on the best-times board.
  6. RESET PROFILE is deliberately two presses within 4 seconds; the first press renames the button to PRESS AGAIN and says what will be lost. BACK returns to the start screen.

Each step is photographed in Evidence/ (E1 to E4, listed in section 8).

3. The save file

Location

Platform Path
Android /data/data/com.defaultcompany.dama/files/Dama/profile.json (that is, Application.persistentDataPath/Dama/profile.json)
Windows editor C:/Users/<user>/AppData/LocalLow/DefaultCompany/dama/Dama/profile.json

The folder is the app's private sandbox. No other app on the phone can read it, and uninstalling the game deletes it. Nothing is written anywhere else.

Format

One UTF-8 JSON envelope: an int schema for future migrations, a string sig holding the signature, and the payload the signature covers.

{
    "schema": 1,
    "sig": "9c1f6a0d3b7e42f8a5d0c94e17b3a6f25d8c4e0b91a7f36c2d5e8b4a1f907c3de",
    "payload": {
        "schema": 1,
        "playerName": "Charibelle G.",
        "playerSide": 1,
        "wins": 2,
        "losses": 1,
        "draws": 0,
        "currentStreak": 0,
        "bestStreak": 2,
        "lastMatchId": 3,
        "lastPlayedUtc": "2026-11-26T03:12:10Z",
        "recent": [
            {
                "matchId": 3,
                "result": "LOSS",
                "winner": "BLUE",
                "seconds": 62.0,
                "redPieces": 1,
                "bluePieces": 4,
                "whenUtc": "2026-11-26T03:12:10Z"
            }
        ]
    }
}

The sig value above is illustrative - a real file's signature is the HMAC of that exact payload, so it changes whenever any field changes.

Field Type Rule enforced by PlayerProfile
schema int A file newer than SchemaVersion (1) is refused and quarantined rather than guessed at
sig string Lowercase hex HMAC-SHA256 over the canonical payload, compared as an ordinal string
payload.playerName string Trimmed, control characters stripped, runs of spaces collapsed, capped at 16; blank becomes PLAYER
payload.playerSide int Only 1 (RED) or 2 (BLUE) is accepted; anything else falls back to RED
payload.wins / losses / draws int Floored at 0 after the signature passes
payload.currentStreak int Floored at 0; a loss resets it, a draw keeps it
payload.bestStreak int Raised to at least currentStreak, so an edited save cannot claim a best streak below the current one
payload.lastMatchId int Floored at 0. RecordMatch refuses any id at or below it, which is what makes a double bank impossible
payload.recent list Nulls removed, oldest entries dropped past 20

4. Integrity design

Six decisions, in the order they protect the file.

4.1 The save is signed, and the signature is over the canonical payload. On write, the payload is serialised with JsonUtility.ToJson(state) and that exact string is signed. On read, the file is parsed and the payload is re-serialised with the same call before the signature is recomputed. Signing the raw text of the file instead would have made the check depend on whitespace and key order, so a cosmetic difference would have looked like tampering. The canonical form is the contract.

4.2 The key is per install and never shipped. ComputeSignature keys HMAC-SHA256 with 16 bytes generated by RandomNumberGenerator.Create() on the first save and kept in PlayerPrefs["profile.salt"] as base64. There is no constant in the source, so a compile of the game does not contain the key, and two installs sign differently.

4.3 The write is atomic. The JSON goes to profile.json.tmp, the old file is deleted, and the temp file is moved into place. A process killed mid-write leaves a .tmp file behind, never a half-written profile.json where a complete one used to be.

4.4 A rejected file is quarantined, not destroyed. When parsing or the signature check fails, the file is moved to profile.rejected.json and a fresh default profile starts. A player's only copy is never overwritten by a game that did not understand it, and if this ever happens for real, the rejected file is the evidence.

4.5 Numbers are clamped even when the signature passes. A correctly signed file is still a file, and a correctly signed file is exactly what an attacker holding the salt produces. So after the signature passes, negatives are floored, bestStreak is raised to at least currentStreak, the name is re-sanitised and the recent list is cleaned. Conservative clamping means an edited save degrades into something plausible instead of something impossible.

4.6 There is exactly one gate, and it is a match id. DamaBoard fixes currentMatchId = PlayerProfile.LastMatchId + 1 when a match starts. BankMatch returns early when currentMatchId <= PlayerProfile.LastMatchId, and PlayerProfile.RecordMatch independently refuses any id at or below lastMatchId. Two independent guards for the same failure, because an inflated record is the failure mode that actually matters to a player.

Rejected alternative: encrypting the file. There is no key the attacker does not have, so encryption would add code, a decryption-failure path and the false impression of a guarantee, without changing who can produce a valid file. It is not in the build, and section 5 says so on the record.

5. What the signature does not do (the honest limit)

The save is tamper-evident, not tamper-proof.

  • It is not encrypted. Anyone who can read the file can read the name, the side and the record.
  • The salt lives on the same device as the file. A determined local attacker can read it and re-sign an edited save, and the game will accept that file.
  • There is no server, no account and no online leaderboard, so there is nothing to check the record against. For an offline hot-seat board game that is the true ceiling.

This is recorded in the check log as L15 KNOWN LIMIT rather than passed off as a pass, and it is repeated in the README under known limitations.

About the count - stated plainly

The log contains fifteen rows, L1 to L15, which is the shape the weekly task asks for. Fourteen of them are assertions that can fail. The fifteenth is not an assertion: it records what the design does not protect against, and it prints as KNOWN LIMIT every run.

A test that "passes" a limitation would be a dishonest test, so L15 is not counted as a pass and the total line says so. The alternative - writing a check that always succeeds and calling it a fifteenth pass - would have made this document look stronger and told the reader less.

Two details worth stating, because they are what the checks are worth

  • L12 plants a save whose numbers are impossible but whose signature is correct. It passes the signature gate and is then clamped to wins=0 losses=0. That is the proof that the signature is not being used as the only defence.
  • L14 does not merely fail to crash. LastError carries the operating system's own message and the panel prints it, so a real player would see "Could not save." followed by the reason instead of a silent no-op.
