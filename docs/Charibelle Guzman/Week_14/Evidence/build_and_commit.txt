These are the same values Week 13 recorded. They were not changed this week and
nothing in Week 14 needed them changed: an accessibility pass and an audio layer
do not touch the platform configuration. They are recorded again because they are
the settings a build of THIS commit would use, and the audit's touch floor is
derived from the screen class they imply.

Why these values, in one line each:
  - API 26 is the floor current Unity 6 Android builds support, so no device that
    can install the game is excluded by a needless restriction.
  - ARM64 only: 32-bit ARM is no longer accepted by Google Play for new
    submissions, and one architecture keeps the download small.
  - IL2CPP: a native build is harder to decompile than the Mono backend, which
    backs up the Week 13 point that the delivered game resists casual editing.
  - No internet permission: Dama is offline and two-player. The app declares only
    what it uses.

----------------------------------------------------------------------------
2. HOW THESE SETTINGS ARE APPLIED
----------------------------------------------------------------------------
They are not clicked together by hand. They are applied by a script:

  Assets/Scripts/Editor/AndroidBuildSetup.cs
  Unity menu:  Tools > Android > Apply Mobile Build Settings

Re-running it is idempotent - it re-applies the same values - so the platform
declaration can be reproduced from the repository instead of described.

4. WHAT WAS BUILT FOR THIS WEEK
----------------------------------------------------------------------------
No APK or AAB is attached to this submission.

The runtime evidence for Week 14 is the Editor in play mode, driven by
Tools > Dama > Week 14 > 3. Capture Week 14 Evidence. Those three captures
(E1-E3 in the Evidence folder) are of the real GameCanvas in the real
DamaGame.unity scene, with the real GameFeedback component playing the five
clips and the real profile store being written.

The accessibility audit runs in the Editor, not in play mode, because it walks
the scene's canvas hierarchy including the panels that are switched off. That is
a deliberate difference from the captures: the audit measures the layout as
authored, and the captures prove the layout as drawn.

Stated plainly, so there is no false impression: "the game runs in the Editor"
and "the game was installed on a phone and launched" are two different claims.
Only the first one is made here. Consequences of that limit are named where they
belong - the haptic in PT6 section 5, the 96 px floor's derivation in both audit
log headers, and the phone-size question in the README limitations.
