What is still not measured, and why that is not a pass

HUDPanel/TurnText (34 px) and HUDPanel/CountsText (28 px) have no opaque backdrop - they are drawn straight over the 3D board, so their contrast changes as pieces move. Both logs report them NOT MEASURABLE, both logs say so in the total line, and neither is counted as a pass in either run. The audit's closing line says what the whole exercise is worth:

"Every measurable control meets the three thresholds. That is a floor, not a ceiling: an audit cannot see an accessible game, and it cannot read a label that is the right size and still says nothing."

One near-miss, stated rather than rounded up

ProfilePanel/NameInput/Placeholder passes at 3.01:1 against a 3.0 requirement. It is 28 px, so it is judged as large text and needs only 3.0. A hundredth of a ratio point is not a pass worth being pleased about, and the repair pass deliberately does not touch a passing control, so it is left as it is and listed here and in the README.

4. The three bugs the repair pass had, and how they were found

The repair script is itself code, and it broke things before it fixed them. All three failures were caught by running it, looking at the result, and measuring - not by reading it.

4.1 It pushed controls off the bottom of their panels. The de-overlap pass sorted siblings by rect.yMax to find what sat where. RectTransform.rect is pivot-local: yMax is a distance from that control's own pivot, not a position in the panel, so two controls in different rows compared as though they were in the same place and the pass shoved them 96 to 137 px down. Some left the canvas entirely. The fix was a PanelRect() helper that takes real world corners (GetWorldCorners) and converts them into the panel's local space with InverseTransformPoint, so every comparison is in one coordinate system. The damaged positions were then restored with a one-off scripted pass before running again.

4.2 It clamped to zero instead of the panel's floor. The follow-up clamp compared a control's bottom against 0 - the panel's pivot - rather than panel.rect.yMin. On a panel whose pivot sits at its middle, "0" is the middle of the screen, and the clamp happily left controls parked below a boundary it thought was a wall.

4.3 A row nudge moved one button of three. Three buttons sit on one row of the profile panel - BACK, SAVE, RESET - at three different anchors. The nudge looked for a control at a given position, found the first, and left the other two behind: a row that visibly broke apart. The fix is ShiftRow(), which selects siblings by anchorMin.y being equal rather than by where they happen to be, and moves all of them by the same amount.

After the fix, the final geometry, printed by the script and visible in E3:

Control Size Anchor Note
NameInput 420 x 96 (0.395, 0.72) Raised; nudged down 4.6 px to keep a 12 px gap under the label
SideButton 260 x 96 (0.665, 0.72) Raised; sits beside the name field, not under it
BackButton 200 x 96 (0.220, 0.19) Bottom row, nudged down 25.3 px as one row
SaveButton 200 x 96 (0.500, 0.19) Same row
ResetButton 200 x 96 (0.780, 0.19) Same row

Idempotence, proved by hash. Running the pass a second time prints

[AccessibilityBuild] fingerprint 4C3E2E0C -> 4C3E2E0C (UNCHANGED - this run was a no-op)

The fingerprint covers every control's anchor, size and position. A build script that nudges the UI by a pixel on every run would make each new screenshot incomparable with the evidence already submitted, so "it is idempotent" is a measured claim here, not a design intention.

6. Machine pre-test results

Evidence/autopilot_session.md is the full record. It is a machine pre-test: an automated agent played the same five tasks a volunteer will be given, to find mechanical defects before a person's twenty minutes are spent on them.

Task What the run did Time
T1 - profile name and save PLAYTEST -> PLAYTEST2, status line confirmed, profile.json written 1.6 s
T2 - start a match Start panel hidden, HUD Turn: RED, Red: 12 Blue: 12 2.8 s
T3 - catch a piece BLUE count 12 -> 11 on a real click pair 12.9 s
T4 - crown a Dama RED chain (4,3) x(5,4) -> (6,5), then x(5,6) -> (4,7); ring visible, BLUE 10 13.3 s
T5 - finish the match RED WIN!, profile matches 5 -> 6, wins 3 -> 4 53.2 s

The match ended 6-1 with BLUE still holding a piece but having no legal move - the immobilisation rule, exercised for real.

The four findings

# Finding Severity
M1 The five button captions are 14 px while every other label is 17-110 px. START, II PAUSE, RESUME, RESTART (pause) and RESTART (end screen) are the smallest strings in the game, on the largest controls. The audit cannot see this - it measures contrast and box height, not type size S3
M2 There is no way back to the start screen once a match has begun. The pause panel offers RESUME, RESTART, SOUND; the end screen offers RESTART. PROFILE exists only on the start screen, so a name or side cannot be changed without restarting S2
M3 The end screen states only the winner. RED WIN! and RESTART: no final counts, and nothing that explains a win by immobilisation, in a match that ended 6-1 S3
M4 ProfilePanel/StatusText is the faintest text on the profile panel at 17 px, beside a 20 px best-times line. Legible in the capture, marginal at arm's length S4

M2 is the one to act on first: it is the only finding that stops a player doing something they would reasonably want to, and it lengthens every future session for no reason.

The harness's own contradiction, disclosed

The run raised an alert at the start - "the game didn't answer session within 60 s; the run played the editor's own level" - and then played Dama anyway. Every observation in its trace names a DamaGame object (pointer targets on DamaGame:/DamaBoard/Squares/..., the HUD text, the profile store, the win panel). The alert is recorded in autopilot_session.md section 5 rather than dropped, because a harness that contradicts itself should be described, not smoothed over. The findings above are drawn only from observations that name a DamaGame object or a Dama script.

A side effect to disclose: the run banked a sixth match into the local profile on this machine (matches 5 -> 6, wins 4). The profile is a local file, and the Week 13 two-press RESET erases it.

Why the machine pre-test is not a substitute

It completed the five tasks in 53.2 seconds because it was told what to do - catch a piece, crown a man. A volunteer will not be told, and the gap between those two situations is the entire reason to run a session. The pre-test found four mechanical defects; it cannot say whether a rule is understandable, how long understanding takes, or at what moment a player gives up.

8. Reproducing every check

Evidence/HOW_TO_RERUN.txt holds the exact procedure. Three editor menu items produce everything:

Tools > Dama > Week 14 > 1. Run Accessibility Audit     -> a11y_baseline.log, then a11y_after.log
Tools > Dama > Week 14 > 2. Apply Accessibility Fixes   -> the repairs, and a fingerprint to prove no-op
Tools > Dama > Week 14 > 3. Capture Week 14 Evidence    -> E1-E3 + feedback_lines.txt, in play mode

Two project quirks that will break a naive re-run, both recorded there: domain reload on entering play mode is disabled, so Editor-time statics survive into play mode and every harness resets the profile first; and the game sets Time.timeScale = 0 when it pauses or ends, so any new timing code must use unscaled time.

One trap specific to this week: the audit decides its own label with File.Exists(BaselinePath) ? "after" : "baseline". Deleting a11y_baseline.log silently relabels the next run as a baseline - which would quietly destroy the comparison this whole document rests on.
