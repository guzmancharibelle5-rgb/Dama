The canvas scaler is what makes a touch floor definable at all: 48 dp at xxhdpi is 144 physical pixels, and 144 / 1.50 = 96 canvas pixels. That derivation is written into the header of both audit logs so the number is not an opinion. The two type floors - 20 px for a caption, 18 px for any other label - are a project decision, not a WCAG number, and both audit headers say so: 20 px is roughly 13.3 dp at this scale.

What the environment cannot decide is stated in Evidence/environment.md and repeated here, because an acceptance record that hides its blind spots is worth less than one that names them:

  • No handset. adb devices returns List of devices attached with no serial. No device, no logcat.
  • No APK. Editor-only evidence by decision; the Android settings are applied and recorded but nothing was installed.
  • One renderer, one resolution. Every measurement is against the 1280 x 720 reference on one machine.
  • Domain reload disabled means Editor-time statics survive into play mode, so both harnesses reset the profile store to the default data directory before seeding. That reset wipes the real local profile; the consequence is recorded in environment.md section 3 rather than fixed by deleting the code.

3. Acceptance criteria, written before the run

The module's completion checkpoint is the frame: no unresolved defect may cause data loss, prevent completion of the core gameplay loop, expose another player's information, or repeatedly crash the application. Those four conditions were turned into four criteria, and two more were added from the Week 14 audit, before any test was executed. The order matters: a criterion written after seeing the result is a rationalisation.

Twenty-eight cases. Every one of them records a measured value, not a sentence: pieces=24, turn='Turn: RED', offered=[(1,1), (2,2), ... (6,6)], repeatRefused=True, timeScale=1.00. A case that can only print PASS is a case that cannot fail.

The rules are seeded by reflection into the board's grid and then driven through the game's own entry points (ExecuteMove, EndTurn, CheckForWin), so a case exercises the same code a tap does, not a parallel copy of it.

Open defects after the pass: none. Open S1/S2: none.

Two decisions inside those corrections are worth naming, because they are the ones a reviewer would otherwise have to guess at:

  • DeclareWinner keeps a single parameter. The plan said it would take (winner, reason). It does not. A second parameter would have made Week14Checks's reflection lookup throw AmbiguousMatchException, and it would have created a second place for the winner and the reason to disagree. The method derives both from the board it is already looking at.
  • The label wins the tension in DEF-15-04. Lightening a fill to buy a visible edge spends the contrast of the white text on it. The pass is bounded on both sides - 3.15:1 for the edge, 4.6:1 for the text - and the text bound is the harder one. All three controls still pass their own label contrast at 6.59:1, 6.63:1 and 6.64:1.

8. Regression: what the fixes cost, and what moved

A fix pass that is only checked against the failing cases is not a regression test. Three independent checks were made.

1. The repair script is idempotent, by fingerprint. Week15Fixes.Fingerprint() hashes the layout it is about to change. The first run reports 3 control(s) created, 6 label(s) resized, 5 fill(s) lightened and a hash change 5BB40B04 -> 8C0D040E. The second run reports 0 / 0 / 0 and 8C0D040E -> 8C0D040E (UNCHANGED - this run was a no-op). Its Verify() step then prints 13 caption(s) and 14 label(s), 0 below its size floor. 0 button fill(s) below 3.0:1.

2. The audit is re-run in full, and every baseline row is paired. a11y_delta_week15.txt re-measures all 109 scored rows and reports 0 REGRESSED and 0 DROPPED - no baseline row was quietly lost between the two runs. Fifteen rows keep their verdict while their measurement moved, and each is paired rather than ignored. Two examples, both copied from the delta: StartPanel/StartButton/Text L still passes with height=100.0, but the requirement it must clear rose from need=15.7 to need=24.6 as the caption went from 14 to 22 px; and PausePanel/SoundButton/Text C dropped from 9.29:1 to 6.59:1 when the fill behind it was lightened from #404759 to #545D74. Both still pass. Both are closer to their line than they were.

3. The full case suite is re-run, not just the failures. The final run is 27 passed, 0 failed, 1 blocked - the same 28 cases, with TC-A11Y-01 now measuring 13 buttons where the baseline measured 11. The two arrivals are the two MENU buttons, and TC-A11Y-02 still reports 0 overlapping pairs with them in place.

The residual risk this section names rather than hides: three controls now sit between 3.16:1 and 3.19:1 against a 3.0 floor, and ProfilePanel/SideButton sits at 3.03:1. The next edit to any of those fills puts them back under the line, and nothing will warn anyone. The audit is to be re-run before every submission.
