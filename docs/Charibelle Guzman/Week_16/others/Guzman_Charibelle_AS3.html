2. Change 1 - allocation-free move generation

Revision: 356e99f. File: Assets/Scripts/DamaBoard.cs.

What was wrong

GetCaptureMoves and GetSimpleMoves each built a fresh List<Vector2Int> on every call, and GetSelectableMoves built another for the mandatory-capture refusal. Because CheckForWin calls HasAnyLegalMove at the end of every turn, and HasAnyLegalMove asks those generators about all 12 pieces, the game allocated a collection per piece per turn, forever.

Baseline measurement: 556.7 B for one GetSelectableMoves, 6,975.9 B for one whole-board legality scan (R² 1.00 on both), against a project target of 0 B per turn.

What changed

  • One reusable buffer per generator. captureBuffer and simpleBuffer are instance List<Vector2Int>(32) fields; the generators write into them and return them.
  • A shared empty result for the mandatory-capture refusal, so refusing costs nothing.
  • HasCaptureAt(x, y) / HasSimpleMoveAt(x, y) - the probe form of the same question, answered with .Count > 0 instead of a list built for a caller that only wanted a yes or a no. These back PlayerHasCapture and HasAnyLegalMove.
  • HasAnyLegalMove asks the side-wide question once. bool mustCapture = PlayerHasCapture(me) is hoisted out of the loop instead of being re-derived per piece.
  • A one-time [Perf] log states the new contract in the console, so the behaviour is visible in a build log and not only in a source comment.

The contract this creates, and how it was made safe

A generator now returns a shared buffer, valid only until that generator is next called. A caller that stored the list would silently see it change. Every call site was audited before the change:

caller what it does with the list
HandleTap selectedMoves.AddRange(moves) immediately
ExecuteMove (capture chain) reads continuations.Count, then AddRange into selectedMoves
RehighlightChain selectedMoves.AddRange(...)
HasAnyLegalMove / PlayerHasCapture reads .Count through the probe helpers

None stores it, and the nesting is strictly sequential (GetSelectableMoves -> GetCaptureMoves -> PlayerHasCapture -> GetCaptureMoves), so no call can invalidate a list another call is reading. The contract is written into the field comment for whoever touches this next.

Measured result

fixture before after reading
one GetSelectableMoves 556.7 B +/- 3.3 (R² 1.00) -6.8 B +/- 4.2 (R² 0.25) below the resolution of the method - and 556.7 B removed
one whole-board legality scan (per turn) 6,975.9 B +/- 0.1 (R² 1.00) -0.1 B +/- 0.1 (R² 0.25) PT-2 met

The R² falling to 0.25 is the signature of success, not of failure: a fit through a real per-call cost has R² near 1; a fit through noise has R² near 0. The instrument still works - the intercept and the Editor-wide column still move - there is simply nothing left for it to find.

3. Change 2 - piece pooling, cached binding, and no strings on the hot path

Revision: bb7e7f3. File: Assets/Scripts/DamaBoard.cs (plus harness seams, section 4).

What was wrong

RestartGame destroyed 24 piece GameObjects and created 24 new ones, each with an interpolated name and a freshly added SpriteRenderer. ExecuteMove renamed a piece with another interpolation on every move. PromoteToDama located a crown with Transform.Find, and BindLayout resolved 64 squares with a per-cell Transform.Find plus a name.Split('_') per piece.

Baseline measurement: 5,701.2 B per restart (R² 0.99); worst restart frame 5.296 ms.

What changed

  • A piece pool. A piece that leaves the board - captured, or cleared by a restart - is parked under an inactive PiecePool root and rented again. A restart releases what is on the board and rents 24 objects instead of destroying and creating them. Because the pool root is inactive and is not under Pieces, nothing that iterates the board's pieces ever sees a parked one.
  • Prebuilt piece names. pieceNames[side, cell] is built once at type initialisation, so neither a rent nor a move formats a string.
  • Crowns found by child index (CrownChild) instead of Transform.Find, and kept on the pooled object: promoting a rented piece only re-activates its crown instead of creating one.
  • BindLayout reads its squares by child index, x * Size + y, with a positional check (IsSquareAt); Transform.Find remains as the fallback for a hierarchy that was hand-reordered. isKing now comes from a crown's active state instead of a name lookup.
  • A one-time [Perf] log records how many pieces were parked the first time the pool path ran.

Measured result

metric before after reading
one restart incl. profile write 5,596.2 B +/- 109.4 (R² 1.00) -1,665.5 B +/- 1,704.1 (R² 0.11) indistinguishable from 0 B; at most ~1.7 KB at two standard errors, at least a 69% reduction
worst restart frame 5.296 ms (baseline) 5.154 ms under the 16.7 ms budget; not claimed as an improvement
mean restart frame 3.103 ms 3.668 ms within the noise of nine samples per run

The frame figure is deliberately not claimed as a win. Nine samples (3 restarts x 3 frames) per run, with worst-frame values of 5.296 / 8.099 / 5.154 ms across the three runs, cannot separate the effect from the noise. What the bytes can show, they show; what they cannot, this document says.

An honest note on frame time: mean frame is 2.062 ms at baseline and 2.181 ms at the end, which is +0.119 ms (+5.8%). That is not a regression from this work. That is why the allocation fixture, not the frame mean, is the decision metric for this week (see Evidence/method.md).

8. What this milestone does not prove

  • Nothing about a phone. Editor play mode, one machine, one resolution, no APK, adb has no device. Device performance and compatibility stay BLOCKED.
  • No rendering claim. Draw calls and batches read 0 in every run while the scene was drawing, so they are recorded as NOT MEASURABLE - not as an improvement and not as a problem.
  • No battery, thermal or GPU-time claim.
  • The restart frame time is not claimed as improved, only as still passing: nine samples per run cannot support more.
  • Long sessions were not profiled; the pool's session-long memory cost is reasoned about, not measured.
