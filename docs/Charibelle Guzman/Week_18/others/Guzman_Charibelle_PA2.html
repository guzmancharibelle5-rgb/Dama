2. The game

Dama is draughts as it is played in the Philippines: an 8x8 board, twelve men a side, two people taking turns on one phone. Three rules make it Dama rather than checkers:

  • A capture must be taken. If a jump exists for the player to move, the non-capturing moves are not offered at all — they are not legal moves that are discouraged, they are absent.
  • A capture chains. A man that lands on a square from which another jump is available keeps going until the chain ends on its own.
  • The king flies. A man that reaches the far row is crowned a Dama and may move any distance along any diagonal, in any direction.

A match ends when a side has no men left, or has men but no legal move.

Target player. Students and young adults who played agawan base, patintero or dama as children, on a mid-range Android phone, one device shared by two players. That decided three things that are visible in the build: every control clears a 96 canvas-pixel touch floor because two people are reaching for the same glass; the whole board is drawn in 2D from the top so a player can read it across a table; and the profile system records a local record because the two players are not on separate devices and have no accounts.

3. The submitted build — and why there is none

The module asks for an installable build. This submission does not contain one. Three independent reasons, each sufficient:

  1. No package was ever produced. Weeks 13–18 were scoped to Editor evidence by decision, and no Android build exists for this project.
  2. No signing key exists. androidUseCustomKeystore: 0, and the keystore, alias and password fields are empty. Anything this machine built would be debug-signed.
  3. No device answers adb. Unity's bundled platform-tools return List of devices attached with no serial, so a package could not have been installed or launched anyway.

This is recorded as BLOCKED, not as a pass, in Evidence/final_pre_submission_checklist.md and in Evidence/release_record.md §3, and TC-COMPAT-01 remains BLOCKED in the regression suite. The full record of the attempt, including what the Editor evidence is and is not worth, is Week_17/Evidence/clean_install.md.

Piece File What it owns
Board and rules Assets/Scripts/DamaBoard.cs the 8x8 grid, move generation, chains, crowning, GameState, the seven panels
Player data Assets/Scripts/Profile/PlayerProfile.cs the signed save file and every read and write of it
Profile screen Assets/Scripts/Profile/ProfilePanel.cs the name field, record, best times, side toggle, two-press reset
Release identity Assets/Scripts/Core/ReleaseInfo.cs Version, BundleId, Engine, Platform, Caption(), BuildLine() — all from Application.*

DamaBoard holds rules and UI wiring; it does not know how a save is serialised. PlayerProfile is the only class that touches the save file. ProfilePanel never parses JSON — it asks PlayerProfile.

State machine. GameState is Ready, Playing, Paused, GameOver, Profile, HowTo, Credits. ShowState() is the only place a panel is turned on or off; every panel is therefore reachable and every panel is hideable, which is what TC-REL-05 checks.

6. Security and player data

The save is a JSON envelope with a schema number, a payload and an HMAC signature over the payload. The key is a per-install salt stored beside the file. The store is written atomically — temp file, then move — and a file that fails its signature is set aside as a rejected copy instead of being trusted. Every numeric field is clamped on load, and the match id gate refuses a repeated end-of-match bank.

What that is worth, stated plainly: the save is tamper-evident, not encrypted. The key and the file live on the same device and there is no server to check a record against, so a determined player with a debugger can rewrite their own stats. The design goal was to make an accidental corrupt file recoverable and a casual edit detectable, not to defend against the device's owner. That limit is recorded in Week_13/Evidence/pt5_checks.log as L15 KNOWN LIMIT and is not counted as a pass.

8. Optimisation

Week 16 measured first, then changed two things: move generation was made allocation-free and pieces were pooled instead of destroyed. On the same scene and the same 32-turn replay:

Measure Before After
Allocation per legality scan 6,975.9 B −0.1 B ± 0.1 (below the method's resolution)
Allocation per restart 5,596 B ~1.7 KB or less
Frame time (mean) 2.062 ms unchanged within run noise

The frame claim is deliberately not made: the frame was already far inside a 33.3 ms budget before the change, and the mean moved with the Editor session rather than with the code. What is proven is that the allocation went away. Every performance number in this project is an Editor number; nothing is known about a phone's frame rate, battery or thermals.
