1. Scope of this report

This report describes the code that is being submitted, names the file each behaviour lives in, and records the defects found across Weeks 13–18 and how each one closed. It does not describe a phone, because no build was made and no phone was attached; §9 states what that costs.

2. System shape

One scene, Assets/Scenes/DamaGame.unity, at build index 0. The scene holds a GameCanvas, a board root, and one DamaBoard component that owns both the rules and the UI wiring.

Script Kind Responsibility
Assets/Scripts/DamaBoard.cs runtime 8x8 Cell[,] grid, parallel bool[,] isKing, move generation, chains, crowning, win detection, GameState, the seven panels, HUD
Assets/Scripts/Profile/PlayerProfile.cs runtime, static the save file: load, clamp, sign, write, reset; the only class that touches it
Assets/Scripts/Profile/ProfilePanel.cs runtime the profile screen: name field, record, best times, side toggle, two-press reset
Assets/Scripts/Core/ReleaseInfo.cs runtime, static Version, BundleId, Engine, Platform, Caption(), BuildLine()
Assets/Scripts/Core/GameFeedback.cs runtime move and end-of-match audio
Assets/Scripts/BoardCameraFitter.cs runtime frames the board for the current aspect ratio
Assets/Scripts/MobileRuntimeConfig.cs runtime mobile runtime settings applied at startup

The boundary that matters: DamaBoard decides what happened, ProfilePanel decides what the player sees, and PlayerProfile decides what is stored. No other class opens the save file, which is what makes the data rules (clamping, signature, atomic write) enforceable in one place.

3. The board

The grid is a Cell[,] of 8x8 — DamaBoard.Size is the single source for every loop — plus a parallel bool[,] isKing. A square holds either nothing, a man of one side, or a crowned man; the king flag is kept beside the grid rather than encoded twice, so a crowning changes one boolean and one cell.

Three rules are implemented as constraints on generation rather than as checks after the fact:

  1. Capture is compulsory. GetCaptureMoves is consulted first; if it returns anything, the simple moves are never offered. That is why a player who taps a man with no legal move gets nothing, and why the UI has no "invalid move" path to explain.
  2. Captures chain. After a jump lands, the generator is asked again from the landing square; the chain ends only when no continuation exists.
  3. The Dama flies. A king's move walks the diagonal in both directions until the edge or a piece; a jump over an enemy it can reach is legal from any distance.

Win detection is one predicate used everywhere: CountPieces(side) == 0 || !HasAnyLegalMove(side). It runs after a move and when a seeded position is checked, so the end screen and the tests agree.

A contract worth naming. GetCaptureMoves, GetSimpleMoves and GetSelectableMoves return a shared buffer that is valid only until the same generator is next called. Every current caller consumes it immediately and stores nothing — audited call by call in Week 16 — and the contract is written into the field comment, because a future caller that keeps the list would break the board silently, with no error.

4. State machine and panels

GameState is Ready, Playing, Paused, GameOver, Profile, HowTo, Credits. ShowState() is the only place a panel is toggled, and every panel is reached from exactly one state:

State Panel(s) shown
Ready StartPanel
Playing HUDPanel
Paused HUDPanel + PausePanel
GameOver HUDPanel + WinPanel
Profile ProfilePanel
HowTo HowToPanel
Credits CreditsPanel

The title screen carries five controls in two rows — HOW TO PLAY / START / CREDITS, then PROFILE / EXIT — plus a version caption anchored top-left. Each control is bound by path in CacheUI() (WireButton(canvas, "StartPanel/StartButton", StartGame)), so a control that exists but was never wired is inert. TC-REL-04 exists precisely to catch that: it reads the bound delegate off each button and names the method it resolves to.

ExitButton calls QuitGame(), which logs the build line and then quits — EditorApplication.isPlaying = false under the editor, Application.Quit() in a build. The wire is proven (TC-REL-04); the behaviour on Android is not, because no build has run.

5. Player data

PlayerProfile stores a JSON envelope: a schema number, a payload, and an HMAC signature over the payload. The key is a per-install salt kept beside the file.

Rule Implementation
Atomic write payload written to <file>.tmp, then moved over the real file
Corruption handling a file whose signature fails is copied aside as a rejected record and a default profile is loaded
Clamping every numeric field is clamped to its legal range on load, so a hand-edited 99 wins cannot become 99
Single bank the match id is fixed when the match starts; a second end-of-match call for the same id is refused
One writer no other class reads, signs, writes or deletes the file

On Android the store lives under Application.persistentDataPath, which is built from companyName and productName — …\LocalLow\DefaultCompany\dama\Dama\profile.json. That is why neither of those two fields may change: moving them moves the store and looks exactly like a wipe. The version lives in bundleVersion, which is what Application.version reads.

Stated limit. The signature makes the save tamper-evident, not secret. Key and file share a device, and there is no server; the record is a courtesy, not a boundary.

Both on-screen strings are written by ReleaseInfo at runtime, never typed into a scene label, and TC-REL-01/TC-REL-02 compare them back to Application.version so they cannot drift.

The duplicate-builder defect is the important lesson here. Week17ReleasePanels had no cleanup for the three title buttons it created, so a second run appended a second HOW TO PLAY / CREDITS / EXIT at the same anchored positions: StartPanel held 11 children instead of 8, and the accessibility case reported each control as overlapping itself (DEF-17-05).
